# Security

## Threat model

Treat MCP as an external attack surface, then be precise about what is actually
behind it.

Behind this server is `data/site-mirror.json` — a copy of the published
kanchanflow.com content — and `reference/`, a folder of documentation. No
database, no credential store, no customer record, no third-party API key, and
no write path to anything.

That removes several classes of risk outright, and leaves a smaller set that
still matter. Both halves are stated below, because a security document that only
lists what does not apply is not doing its job.

## Removed by design

| Risk | Why it does not apply |
|---|---|
| Privilege escalation | No privilege levels. Every caller gets the same 24 read-only tools. |
| Cross-workspace access | No workspaces. Nothing here belongs to one customer rather than another. |
| IDOR | No object is owned by anyone. Every id addresses public published content. |
| Destructive operations | No create, update, delete, publish or execute tool exists. |
| Data exfiltration | Everything served is already public on kanchanflow.com. |
| SQL and command injection | No database, no shell, no `eval`, no dynamic `import()` of caller input. |
| SSRF | No tool takes a URL and no tool makes a network request at request time. |

## Enforced

### Input validation
Every tool declares a zod schema; the SDK validates arguments against it before
the handler runs. Enums are closed sets. Numeric bounds are declared. A handler
only ever deals with semantic failures — an unknown slug, a country outside the
seven display markets, a seat count under a plan minimum.

### Path traversal
`kanchanflow_get_reference_document` is not a file reader. `src/reference/loader.ts`
rejects an absolute path, a Windows drive path, a NUL byte and any `..` segment;
normalises what remains; verifies the result resolves under the reference root by
prefix; and then re-checks with `fs.realpathSync` so a symlink cannot point out
of the tree. It serves `.md` and `.json` only, from a pre-built index of regular
files, skipping anything over 512 KB. `../../.env` and `../../package.json` both
come back as `VALIDATION_ERROR`.

### Secret leakage
No tool, resource or prompt returns an environment variable, a token, an internal
hostname or a filesystem path.

- Resources are eight named slices of the mirror, not an arbitrary key
  expression. There is no `kanchanflow://config/<key>` and none can be
  constructed.
- `/health` reports liveness and version only.
- An unmodelled exception returns a generic `INTERNAL_ERROR`; the real message is
  logged server-side because it can contain a path, and is never returned.

### Request abuse
The HTTP transport applies a fixed-window per-IP limit before authentication and
before dispatch, refuses a body over 1 MB unread, and handles every request
statelessly with a fresh server instance. The limiter sweeps expired buckets so a
long-lived process cannot accumulate one per address seen since boot.

The limit is per process. A horizontally scaled deployment gets per-instance
limits — a documented property, not a bug. Put a shared limiter at the edge if
you need a global one.

### Authentication
Optional bearer token on the HTTP transport, compared length-first and then in
constant time. Unset means a public endpoint, which is a legitimate configuration
for public content. See `api/authentication.md`.

### Logging
Structured JSON on stderr. Argument **names** are logged, never values. Tokens
and headers are never logged. Under stdio, stdout carries the protocol, which is
why nothing writes there.

## Prompt injection through stored content

The realistic residual risk, and worth being honest about.

Tool responses carry long prose written for the website — feature descriptions,
connector setup steps, blog paragraphs. A client model reads that text. If
someone with commit access to the website repository wrote an instruction into a
feature description, it would reach a model through this server.

The mitigations are procedural rather than technical, and they are the right ones
for this shape of system:

- Content originates in a reviewed Git repository, not from user submissions.
  There is no path by which an outside party writes into the mirror.
- The mirror is regenerated by an explicit `npm run sync` and committed as a
  reviewable diff. A change to the served text shows up in code review.
- Responses are structured JSON with prose in known fields, so a client can treat
  those fields as data rather than as instructions.

A client should treat all tool output as untrusted content, as it should with any
MCP server.

## AI safety boundaries

The read-only / destructive distinction the MCP specification asks servers to
make is trivial here, and stated explicitly rather than left implied:

- **Every tool is read-only.** All 24 advertise `readOnlyHint: true`,
  `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`.
- **No tool requires confirmation**, because none can change anything. A client
  can call any of them without a user prompt.
- **If a write tool is ever added**, that stops being true. It would need
  authentication, an explicit confirmation contract, and its own section here.
  Nothing in the current design assumes writes will never exist; it just does not
  pretend they do now.
